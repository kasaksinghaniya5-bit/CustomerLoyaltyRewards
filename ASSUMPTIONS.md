# Assumptions

## 1. General Assumptions

1. The application is designed for a factory that sells packaged physical products.
2. The system will initially support one factory and its loyalty programme.
3. Customers will access the application through a web browser.
4. Version 1 will focus on a desktop-first interface.
5. An active internet connection will be required to access the web application, even though the database will run locally during development.

## 2. Product and Reward Code Assumptions

1. Every eligible product package will contain a unique reward code.
2. The factory is responsible for inserting and protecting reward codes inside product packaging.
3. Each reward code can be successfully claimed only once.
4. Product reward codes will be generated by an authorised administrator.
5. Each generated code will retain the points value assigned to it at the time of generation, even if the product's points value changes later.
6. Test codes will be generated for development and testing without requiring customers to purchase physical products.

## 3. Customer Assumptions

1. Customers must register before claiming reward codes.
2. Each customer must have a unique email address and username.
3. Customers must provide valid registration information.
4. Customers are responsible for keeping their login credentials and unclaimed product codes confidential.
5. Customers can claim one product code per submission.

## 4. Points and Redemption Assumptions

1. Points earned through valid product codes do not expire.
2. The default minimum redemption threshold is 100 points.
3. The administrator can configure the minimum redemption threshold.
4. Customers can redeem rewards only when they have sufficient points and the selected reward has available stock.
5. Each redemption generates a unique redemption code.
6. Physical rewards must be collected from an authorised factory outlet.
7. Redemption codes are valid for 30 days by default.
8. If an active redemption is cancelled or expires without collection, the points will be refunded and reserved reward stock will be restored.

## 5. Staff and Administrator Assumptions

1. The system will have three roles: Customer, Administrator and Staff.
2. Customer accounts can be created through public registration.
3. Administrator and Staff accounts cannot be created through public registration.
4. The initial version will have one primary administrator account.
5. The administrator is responsible for creating and managing staff accounts.
6. Staff members can verify redemption codes and confirm physical reward collection.
7. Staff members cannot access product reward code generation or other administrative management functions.
8. Role-based permissions will be enforced by the backend.

## 6. Security and Fraud Prevention Assumptions

1. Product reward codes must be unique and unpredictable.
2. Passwords must be stored using secure password hashing.
3. Authentication and role-based access control must be enforced by the backend.
4. Five consecutive invalid product-code attempts will generate a suspicious activity alert for the administrator.
5. Five consecutive incorrect login attempts will trigger a temporary account lockout.
6. Important administrative actions and points transactions will be recorded for accountability.
7. A unique product code alone cannot guarantee that a customer purchased the product; the factory's packaging and code distribution process is responsible for controlling access to unused codes.

## 7. Notifications and Reporting Assumptions

1. Version 1 will use in-app notifications.
2. Email notifications are outside the initial implementation scope.
3. The system will provide reports that administrators can export in Excel and CSV formats.
4. Customer leaderboard entries will display usernames rather than personal names or email addresses.

## 8. Development and Testing Assumptions

1. MongoDB Community Edition will be used as the development database.
2. The frontend and backend will be maintained in separate folders.
3. Git and GitHub will be used for version control.
4. The application will be tested using manually generated test codes and test accounts.
5. Testing will cover valid operations, invalid inputs, duplicate claims, security restrictions and redemption scenarios.

## 9. Future Enhancements

The following features are not part of Version 1 but may be considered later:

- Mobile-responsive interface.
- Customer email verification.
- Email notifications.
- Customer profile editing and username changes.
- Emergency administrator recovery mechanism.
- Additional administrator accounts.
- QR-code-based product code claiming.
- Print-friendly product code sheets.
- Home delivery of physical rewards.
